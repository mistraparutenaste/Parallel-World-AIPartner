## 特定した原因

1. LLM streamはSSEの`[DONE]`を受信してもtransport EOFまで待っていた。
2. TTSは容量8のqueueが満杯になると、1文の局所的な混雑を同一turn全体の失効へ拡大していた。その結果、合成済みの先頭音声と待機中の全音声も抑止された。
3. TTS adapterのHTTP timeoutが5秒固定だった。12:52:31.003にAivisが長い1文の推論を開始し、アプリは12:52:36.006にtimeout、Aivisは128ms後の12:52:36.134に正常完了（5.13秒）。Engine crashではない。
4. rolling summaryはUser/Assistant roleを捨てて平文連結し、その平文をSystem messageとして再注入していた。さらに直近20件の履歴と、直近4件だけを除外した要約が最大16件重複していた。
5. 実DBの旧summaryは平文2000文字、`through_message_id=62`で、過去の誤答`10, 4`を含んでいた。

## 修正

- `[DONE]`をprotocol完了として即時return。
- TTS queue full時は順序を維持した有限backpressureを適用。
  - 10ms周期でstop/watermarkを確認。
  - 最大5秒で解除されなければ現在の1文だけdropし、turn全体は失効させない。
  - worker切断時は保持workerをclearし、次回再生成可能にする。
  - 新turnでは旧turnを失効し、旧音声を停止する。
- TTS合成timeoutを30秒へ延長し、queue backpressure timeoutは独立した5秒のまま維持。
- rolling summaryを`role_summary_v1` JSONへ変更し、role・否定・推量・引用を保持。
- legacy平文summaryはDBから削除せずpromptからfail-closedで除外し、保存済みrole付き履歴から段階的に再構築。
- summaryのrecent除外件数を通常履歴と同じ20件へ統一。
- user settings / memory / summaryを、untrusted policy付き・閉じタグescape済みJSON境界でSystem contextへ渡し、現在User messageを必ず末尾に保持。
- chat受付・context構築・HTTP header・first delta・SSE `[DONE]`・reply完了の内容非依存タイミングログを追加。

## 遅延の切り分け

- 遅かった`6+7` turnは、LM Studioでprompt eval 1,469 tokens / 1.22秒、generation 839 tokens / 12.22秒、計13.44秒だった。2文字回答に839生成tokenを使っており、モデルの過剰生成が主因。
- 同turnにgateway / IPC / queue stall / timeout / errorはなく、LM完了からアプリ完了も約1秒以内だった。
- 最終INFO計測のLM Studio内訳はprompt eval 2,020 tokens / 1.722秒、generation 3 tokens / 33.5ms、model total 1.756秒だった。一方、POSTからstream完了までは約6秒で、first delta後から`[DONE]`まで約4.03秒を要した。gateway / IPC / queue stallはなく、LM Studio内のstream完了処理またはtemplate互換処理に未計上の待機が残る。
- LM Studioにはoutdated Gemma4 chat template警告があり、requestに`max_tokens`は記録されていない。

## 残るリスク

- LM Studio応答時間にはばらつきがある。遅いturnでは839 tokenの過剰生成、短い最終turnでは3 token生成後から`[DONE]`まで約4.03秒の未計上待機があり、主因はLM Studio／モデル／template側。アプリ側context構築は1ms、HTTP header受信は9msだった。
- 現在のモデルは、複数の文章条件を一度に集約する初回推論で破綻した。式を明示した自己検証では訂正できるため、transportやsummary破損ではなくモデル／template側の推論品質が主因。
- TTS workerが5秒以上まったく進まない場合は、conversation全体ではなく現在の1文だけをdropする設計。音声完全性より会話停止回避を優先している。
- TTS adapter自体のhangは30秒で打ち切る。長い無句読点テキストは1文扱いになるため、将来は文字数上限での分割も検討余地がある。
- `[DONE]`でresponse bodyを閉じるため、HTTP/1.1 keep-alive接続を再利用できないserver実装があり得る。ローカルLM Studioでは連続会話が完了しているが、remote/TLS endpointは別途評価が必要。
